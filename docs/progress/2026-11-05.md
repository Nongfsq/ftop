## Drag-to-Applications DMG (issue 32)

- The owner approved a DMG beside the zip on issue 32 (2026-11-04). `scripts/release.sh`
  now ends with `scripts/dmg.sh`, which copies the stapled `Ftop.app` with an
  `Applications` link into a ULFO image (`diskutil image create from`; `hdiutil create`
  warns it is deprecated), signs the image with the same Developer ID and a timestamp,
  notarizes it, and staples it. No Finder window layout or `.DS_Store` template: the
  contributor's `scripts/dmg.sh` was read as a reference only.
- The zip, its name, and the updater are unchanged; the updater matches the asset by its
  exact zip name, so a DMG on the same release is never downloaded by it.
- READMEs (both languages) offer the DMG (drag to `/Applications`) or the zip (move to
  `~/Applications`), with the command link written for `/Applications` and a note for
  the other folder. `/Applications` is admin-writable, so the updater's
  `canInstall` holds there for an admin account; a standard account would not update
  in place.
- Local dry run on 0.2.8 (not published): zip and DMG notarizations `Accepted`;
  `spctl -a -t open --context context:primary-signature` and `stapler validate` pass on
  the DMG; mounted, it holds `Ftop.app` ("Notarized Developer ID") and the
  `Applications` link. `scripts/check.sh` passed (16 + 51 + 15 tests).
- Not checked: dragging from the mounted DMG in Finder by hand; the first release that
  attaches the DMG.

## End and Force End on a process row (issue 32)

- Built from the owner's reply on issue 32 (2026-11-04). A contributor's branch
  (`lanstar128/ftop`, `feat/process-control-login-storage`) was read as a reference
  only; its settings window and storage reading were declined and are not here. The
  decision doc's section "End and Force End on a process row" holds what was built.
- `ProcessSample.startTime` carries `ri_proc_start_abstime`, read once per process
  beside its app path. `ProcessControlPolicy` (FtopCore) decides; `ProcessControl`
  (FtopSensors) reads the facts and sends `terminate`, `forceTerminate`, SIGTERM or
  SIGKILL; `ProcessEnding` (FtopApp) builds the block's section and the confirmation.
  `ftop-helper` is unchanged.
- Found while checking the real panel: `PROC_PIDTBSDINFO` is refused for another
  user's process without admin rights, so WindowServer read as "Has exited". The user
  now comes from `PROC_PIDT_SHORTBSDINFO`, and a test pins it.
- Checked: `scripts/check.sh`; new tests `ProcessControlPolicyTests` (stale PID,
  exited, protected PIDs ≤ 1 and ftop, other user, unreadable start, folding keeps the
  representative's start time) and `ProcessControlTests` against real child processes
  (SIGTERM, SIGKILL, stale identity never signalled, exited, ftop, launchd, a root
  process, WindowServer); reference images `control-{en,zh}-process` and
  `-process-refused` looked at. On the real panel (a release build run beside the
  installed copy under another bundle id, driven by pointer on a 4K display): the
  block opened on a `yes` row with its PID; Return cancelled the confirmation; End sent
  SIGTERM; WindowServer showed "Another user's" with both actions dimmed and inert;
  Claude's row named the main process (`Contents/MacOS/Claude`), not a helper; a test
  app quit on End and stopped on Force End; the background right-click had no process.
- Not checked: an app that answers End by asking to save or by refusing; a granted
  (setuid) helper listing other users' processes; the strip layouts' busiest process,
  which is not a row and opens the block without a process.
